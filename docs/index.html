Room lifecycle and delivery primitives for your application.

01 / LIFECYCLE

Temporary rooms

Create 1:1 or group invites with optional expiration. Session issuance rechecks invite validity; expiry and explicit revocation end access for issued sessions.

02 / REAL TIME

WebSocket relay

Stream pending encrypted messages and read receipts over WebSocket. HTTP polling provides a fallback.

03 / TRANSPORT

Encrypted payloads

The API relays opaque ciphertext. Clients implement encryption and peer verification; HTTPS protects sessions in transit.

04 / ADMISSION

Participant slots that seal

Two slots for 1:1 rooms; optional limits for groups. Activation accepts invite tokens only in JSON, requires HTTPS outside loopback, and rejects invalid supplied sessions. Authenticated reconnects reuse a slot; link previews use none.

05 / PROTECTION

Optional room passwords

Require a password alongside the invite. Salted scrypt verifiers and rate-limited attempts protect admission.

06 / RETENTION

No permanent server archive

Queued ciphertext is removed after ACK, read, or message TTL. Bounded retry metadata prevents duplicate sends; clients retain local history and room metadata persists separately.

Transparent architecture

A relay, with clear boundaries.

Inspect the implementation ↗
  1. 01 / SENDING CLIENT

    Encrypt before upload.

    Your client manages private keys, verifies peers, and creates an encrypted envelope for each recipient.

    Client → HTTPS / WSS
  2. 02 / YOUR SERVER

    Authenticate and relay.

    Sideword validates revocable sessions and membership, deduplicates send retries, and delivers queued ciphertext over WebSocket or polling.

    FastAPI ↔ SQLite queue
  3. 03 / RECEIVING CLIENT

    Persist, then acknowledge.

    The recipient decrypts and saves locally before acknowledging the exact delivery identity. The server removes acknowledged ciphertext; TTL clears stale deliveries.

    Recipient → exact ACK → deletion

The server sees routing metadata. Password admission trusts the server and HTTPS terminator; it does not replace client-side encryption or peer key verification. The test client pins first-use keys but has no recipient forward secrecy or post-compromise recovery. Read the security review and migration plan.

Included web client: a test/reference tool

The minimal browser client at /client helps validate the server, protocol, and basic chat flow. It is not a production-ready messenger or the main product. Compare its locally calculated fingerprints out of band; first-use pinning cannot prevent initial key substitution or malicious server-delivered code.

Deployment guide ↗Python setup ↗
Self-host with Docker Shell
git clone https://github.com/vladleesi/sideword-chat-server.git
cd sideword-chat-server
cp .env.example .env
# Set a random signing secret and admin credentials.
# Set SIDEWORD_PUBLIC_URL to your HTTPS origin.
docker compose up -d --build

Configure .env before starting. See the guide for HTTPS, persistent storage, and private admin access. Admin password resets revoke sessions and reject logins still using the previous password.
