01 / Capabilities

Small surface.
Clear behavior.

Room lifecycle and delivery primitives for your application.

01 / LIFECYCLE

Temporary rooms

Create personal or group invites with optional expiration. Expiry and revocation disable sessions issued through that invite; other valid sessions retain chat membership. See lifecycle rules.

02 / REAL TIME

WebSocket relay

Deliver queued encrypted messages with separate durable delivery and viewing confirmations over WebSocket, with optional ephemeral participant presence in a shared process. HTTP polling provides the same message delivery flow.

03 / TRANSPORT

Opaque payloads

The API relays ciphertext. Clients implement encryption and peer verification; HTTPS protects sessions in transit.

04 / ADMISSION

Participant slots that seal

Two slots for personal rooms; optional limits for groups. Body-only activation requires HTTPS outside loopback. Authenticated reconnects reuse a slot; link previews use none.

05 / ACCESS

Optional room passwords

Require a password alongside the invite. Salted scrypt verifiers and rate-limited attempts protect admission.

06 / RETENTION

A queue, not an archive

ACK, read, or message TTL removes queued ciphertext. Bounded retry and per-recipient confirmation metadata supports idempotent sends and sender-only status recovery. Clients retain local history; room metadata persists separately.

02 / Architecture

A relay with
clear boundaries.

Inspect the implementation ↗

  1. 01 / ENCRYPT

    Before upload.

    Your client manages private keys, verifies peers, and creates an encrypted envelope for each recipient.

  2. 02 / RELAY

    Authenticate and deliver.

    Sideword validates revocable sessions and membership, deduplicates send retries, and delivers queued ciphertext.

  3. 03 / ACKNOWLEDGE

    After local persistence.

    The recipient decrypts and saves locally before acknowledging the exact delivery identity. ACK removes ciphertext; TTL clears stale deliveries.

Password admission trusts the server and HTTPS terminator; it does not replace client-side encryption or peer key verification. The reference client pins first-use keys but has no recipient forward secrecy or post-compromise recovery. Security review and migration plan ↗

03 / API

A contract for
your client.

API reference ↗
  1. Activate an invite and receive a bearer JWT.
  2. Send per-recipient encrypted envelopes over HTTP.
  3. Receive messages over WebSocket or HTTP polling.
  4. Persist locally, then acknowledge exact delivery.

OpenAPI is available at /docs on your local administration listener. Clients must agree on an authenticated encryption format.

REFERENCE CLIENT

A tool for testing the contract.

The reference client at /client exercises invite activation, encrypted delivery and local history with non-exportable P-256 keys. It is for testing, not a production-ready messenger. Compare peer fingerprints out of band: first-use pinning cannot prevent initial key substitution or malicious server-delivered code. Rooms from before the P-256 update require fresh invites and identities; see the upgrade guide.

04 / Self-host

Run it on
your terms.

MIT-licensed source. FastAPI and SQLite. Run with Docker Compose or directly with Python. Keep administration private and expose the API over HTTPS.

Deployment guide ↗ Python setup ↗
DOCKER COMPOSESHELL
git clone https://github.com/vladleesi/sideword-chat-server.git
cd sideword-chat-server
cp .env.example .env

# Set a random signing secret and admin credentials.
# Set SIDEWORD_PUBLIC_URL to your HTTPS origin.
docker compose up -d --build

Configure .env before starting. Follow the deployment guide for HTTPS, persistent storage, and private administration. GitHub release publication does not deploy your server; update it explicitly.
